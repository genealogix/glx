## [0.0.0-beta.12] - 2026-09-16

### Added

- **`glx merge-driver` — genealogy-aware git merge driver for GLX files** — A hidden `merge-driver` subcommand performs a structural 3-way merge of GLX YAML when git invokes it through `merge.glx.driver`, so two branches editing the same `.glx` file no longer conflict on safe changes. It auto-resolves one-sided edits, identical edits on both sides, additive changes to an assertion's `citations`/`sources`/`media`/`notes` (unioned, with deletes honored), and diverging assertion `value`s where one side carries a strictly higher rank in the standard `confidence_levels` vocabulary (the higher-confidence side wins and an "auto-resolved by the driver" record is written to stderr). Everything else — equal or custom confidence, the same scalar property changed differently on both sides, delete-vs-modify — falls back to git's text merge with a structured per-conflict summary on stderr listing both sides' values plus assertion confidence and citations. The repository's `.gitattributes` now maps `*.glx merge=glx`; users opt in per clone with two `git config merge.glx.*` lines documented in `docs/merge-driver.md`, and until they do git silently uses its default text merge, so clones that skip setup see no behavior change. Closes #293 (#906)
- **Added `glx evidence <person> <property>` command** — Lays out every assertion for one person+property side-by-side, grouped by asserted value, for weighing conflicting evidence during active (brickwall) research. Each value lists its supporting reports (citation ID and resolved source title) with confidence, the report count, and the best confidence in the group; values are ranked by report count then confidence, and a closing line names the best-supported value — or flags an inconclusive tie when the leading values match on both. Place, person, and event reference values resolve to the referenced entity's name; everything else is shown verbatim. The person argument accepts an exact ID or a name search; the property is matched exactly with a case-insensitive fallback. Supports `--archive` and `--format text|json`. Complements `glx analyze` (which only emits one-line conflict warnings) and `glx proof` (#118, summaries of *resolved* questions). Closes #144 (#895)
- **`glx duplicates` — Soundex phonetic-match signal** — Adds a Soundex-based phonetic-match signal (weight `0.10`) to the duplicate-person scoring model, alongside a rebalance of the existing name signal from `0.30` to `0.20` so total weights remain `1.0`. Catches name pairs that are phonetically identical but lexically distant — Schneider/Snider (Levenshtein distance 3), Mueller/Miller, Smyth/Smith — which the prior Levenshtein-plus-nickname-table approach scored well below the 0.60 default threshold. The new signal averages over up to two sub-comparisons (surname and given name); sub-comparisons that cannot run (empty component on either side, single-letter initial on a given name) are skipped rather than scored 0 so the signal interacts cleanly with the existing renormalization rule (#716) and preserves the existing initial-match credit (`isInitialMatch`). Reuses the in-tree `Soundex` already shipped for `PhoneticPersonSearch` (#262), so no new dependency. Closes #704 (#917)
- **`go-glx`: library GEDZIP import via `fs.FS` (`ImportGEDZIP`)** — GEDZIP archive import now lives in `go-glx` as `ImportGEDZIP(bundle fs.FS, logW io.Writer) (*GLXFile, *ImportResult, error)`, taking any `io/fs.FS` filesystem abstraction rather than requiring temporary directory extraction on disk. Entry paths are validated in-memory against directory traversal (`..`), absolute paths, volume prefixes, backslashes, NUL bytes, and duplicate collisions under Unicode case-folding and dot-segment normalization (`ErrGEDZIPInvalidEntry`, `ErrGEDZIPDuplicateEntry`). GEDCOM file discovery defaults to root `gedcom.ged`, falling back to a case-insensitive single `.ged`/`.gedcom` candidate at the archive root or within a single wrapper directory, returning `ErrGEDZIPMissingGedcom` if no candidates exist or `ErrGEDZIPMultipleGedcom` if ambiguous. Media references are resolved relative to the GEDCOM file path (with percent-decoding and case-insensitive matching fallback) and populate `MediaFileSource.MemberPath`. The CLI (`glx`) imports archives directly from `*zip.ReadCloser` without disk extraction, streaming only referenced media files directly to their destination while enforcing entry count and decompressed size limits. (#1141)
- **`go-glx`: exported GEDCOM 5.5.1 BLOB decoder (`DecodeGEDCOMBlob`)** — The BLOB decoder previously lived unexported in the CLI (`decodeGEDCOMBlob` in `glx/media_copy.go`), so library consumers receiving `MediaFileSource.BlobData` had to reimplement the 5.5.1 decoding — including validation and the trailing-group edge cases — themselves. The function now lives in `go-glx` as `DecodeGEDCOMBlob`, together with its sentinel errors `ErrGEDCOMBlobEmpty`, `ErrGEDCOMBlobLength`, and `ErrGEDCOMBlobChar` (moved out of the CLI package and renamed to match), and the CLI is a caller. Pure function, no I/O. The full-group invalid-character error now wraps `ErrGEDCOMBlobChar` like the trailing-group path already did, so all invalid-character failures are detectable via `errors.Is`; both paths report the offending byte — as a quoted character and as hex, since `%q` alone renders any byte above 0x7F as the wrong code point — and its position before the "must be in range '.' to 'm'" hint. Decoding is also more tolerant of exporter whitespace: tabs, vertical tabs and form feeds are now stripped alongside spaces and line breaks, where previously they were rejected as invalid BLOB characters. Prerequisite for library-level GEDZIP import (#1141). (#1140)
- **GEDCOM/GEDZIP import now populates `media.properties.original_filename`** — The standard `original_filename` media property ("Original filename before import or renaming") was defined in the vocabulary but never populated by any import path. Relative `FILE` references — including media bundled in a GEDZIP archive, whose entries flow through the same conversion path — now record the source file's basename (pre-canonicalization, pre-rename) when the file is copied into `media/files/`. This preserves the source name in the scenario the property was defined for: a basename collision renames the stored file (`photo.jpg` → `photo-2.jpg`), which previously lost the original name entirely. URL and absolute-path references are unaffected (their URI is preserved verbatim, so nothing is renamed), BLOB-derived files get no entry (their filename is synthesized at import), and an `original_filename` a source already carries is never overwritten. Because a GEDCOM 7.0 `FILE` payload is a URI reference, a percent-encoded basename is decoded before it is recorded (`CharlotteBront%C3%AB.jpg` → `CharlotteBrontë.jpg`), while GEDCOM 5.5.1 payloads are plain paths recorded verbatim so a literal `%` is never mangled; a 7.0 encoding that is malformed, or that decodes to something other than a bare filename (a path separator, a control character, an invisible or bidirectional format character — the ZWNJ/ZWJ joiners used in Persian/Arabic, Indic, and emoji filenames are allowed — invalid UTF-8, `.`/`..`), keeps the raw basename. A `FILE` ref already pointing into `media/files/` — the shape a GLX→GEDCOM export produces — is not stamped while its name is untouched, so a GLX→GEDCOM→GLX round trip cannot fabricate false provenance; if the new import itself collision-renames such a ref (merging two exports), the pre-rename basename is real information and is recorded. Re-running an import of a previously imported GEDCOM stamps the new property on every other relative-`FILE` media entity — additive, but visible when diffing against the earlier archive. Purely additive for round-trips: GEDCOM export emits `uri` verbatim and maps no tag to the property. Adds `MediaPropertyOriginalFilename`/`MediaPropertyBlobSize` constants to `go-glx`. (#1121)

- **`glx publish` — static HTML site generator** — Exports a GLX archive as a self-contained, browsable website for sharing with non-technical family. Generates a landing page with archive stats and an alphabetical person list, a profile page per person (vital facts, hierarchical birth/death places, a life timeline including family events, linked parents/spouses/children/siblings, supporting sources with citation locators and quotes, notes, and a media gallery), source and place indexes (places with coordinates link to OpenStreetMap), and a client-side search page. Output is a plain directory of HTML/CSS/JS — no server, database, or build tooling — that works when opened directly via `file://` (the search index loads as a `<script>`, not `fetch`) or hosted anywhere (GitHub Pages, S3, Netlify). Templates and assets are embedded in the binary. Styling is responsive with a light/dark toggle and print-friendly profile pages, and all archive content is HTML-escaped. Flags: `--output`/`-o` (default `./site`), `--embed-media` to inline images as base64, `--living` to redact likely-living people before publishing (reusing the `--privatize-living` redaction), and `--title`. Implements the first phase of the read-only web viewer; interactive SVG pedigree/descendancy charts, a visual timeline view, embedded maps, and theming config are tracked as follow-ups. (#91) Renamed from `glx view` before release to avoid ambiguity with `glx serve` and to name the artifact it produces; the `--serve`/`--port` preview flags were dropped in the same change, since `glx serve` now owns local preview (#970).
- **Git Workflow Guide (`docs/guides/git-workflow.md`)** — New user guide documenting how to actually use Git workflows for genealogy research, filling the gap behind the "Git-native" headline feature: setting up an archive repository (`git init` after `glx init`, line-ending pinning, private-by-default remotes for living-person data), the edit→`glx validate`→commit research cycle with a pre-commit validation hook, branch-based research (hypothesis branches carrying `status: speculative` assertions, merged as `proven` when confirmed or — deliberately — merged as `disproven` when refuted, so negative findings stay on the record), collaboration patterns (shared-repository for family teams, fork-and-PR maintainer model for societies, PR review as genealogical proof-standard review, CI validation), merging and conflict resolution (the `git merge` vs `glx merge` distinction, resolving textual conflicts vs recording evidential conflicts as `status: disputed`, post-merge `glx validate`/`glx duplicates`), history as a research log (`git log --follow`, `git blame`, milestone tags, correct-don't-erase), and scale concerns (Git LFS for `media/files/`, partial clone). Registered in the website nav and guides sidebar, and cross-linked from the Quickstart, Best Practices, and Hands-On CLI guides. Closes #508.
- **Deterministic memory-file drift detection (`make check-memory-drift`)** — A new offline, API-key-free Go tool under `tools/memcheck` checks every `CLAUDE.md` (and `AGENTS.md` if adopted) against the repository and fails when an instruction has rotted: it asserts that every referenced `make` target exists in the `Makefile`, every concrete file/directory path resolves on disk (relative to the repo root or the memory file's own directory), and every `github.com/<org>/<repo>` import path under the module's org matches the `go.mod` module line. It closes the project's own dogfooding gap (it lints docs↔schema parity in CI but not memory-file↔reality parity) and runs as a dedicated CI job in `validate-spec.yml` alongside `check-code-drift`. Path references are recognized syntactically (a slash plus a known file extension, or a multi-segment trailing-slash directory) so look-alikes such as `actions/checkout`, `os/exec`, and the `claude/` branch prefix don't produce false positives; intentional exceptions live in `.claude/memory-drift-allowlist.yaml`. Surfaced and corrected two stale fixture paths in the root `CLAUDE.md` in the process. (#1053, epic #1016)
- **`glx serve` — local browser-based read-only archive viewer** — A new command that starts a small local web server and prints a URL to open in your browser, serving an interactive, dependency-free viewer for a GLX archive: a dashboard (entity counts, assertion-confidence distribution, evidence coverage), browsable/filterable person profiles (names, vitals, chronological event timeline, family links, and assertions with their resolved citation/source evidence), interactive SVG pedigree and descendancy charts, and a source/citation browser. This is Phase 1 (read-only viewer) of the visual editor proposed in #93 — the bridge from "tool for technical genealogists" to "tool for all genealogists." The UI is a self-contained static bundle embedded in the binary (Go `embed.FS` + vanilla JS, no build step or network access); data is served as JSON over `/api/*` and rendered client-side. The server binds to `127.0.0.1` by default (warning when bound to a non-loopback host), supports `--host`/`--port` (use `--port 0` for any free port), reuses the archive-loading and relationship-traversal helpers shared with `glx summary`/`stats`, and loads the archive once at startup (restart to pick up external edits; live file watching is a later phase). (#93)
- **`glx migrations` — track geographic movement patterns** — New read command that traces a person's geographic movement over time by collecting every dated place observation: events the person participated in (birth, census, marriage, …), their children's birth events (a child's birthplace is evidence of the parent's residence at that date), and `residence` property values in all three property shapes (plain string, structured map, temporal list). Observations are sorted chronologically and each change of region is reported as a movement (e.g. `Florida → Wisconsin (ABT 1832 – ABT 1852)`). Regions compare at the state/region level of the place hierarchy — the topmost ancestor below the country/continent level — and pre-statehood territories match their successor states ("Florida Territory" equals "Florida"), so a birth in a territory followed by a census in the later state doesn't read as a move. `--pattern "Florida,Wisconsin"` searches the whole archive instead, for persons whose region sequence contains the given places in chronological order (matching region names or any name in the place hierarchy path) — knowing who else made the same migration narrows the search for a person's family. `--family` also prints the timelines of the person's immediate family (spouses, parents, children), and `--format json` emits the report on the machine-readable stream so `glx --quiet migrations … --format json` stays scriptable. Not to be confused with `glx migrate`, which upgrades archive data. (#114)
- **GEDCOM import/export: FAM.NCHI (number of children)** — The GEDCOM `FAM.NCHI` tag, previously parsed but silently dropped, is now stored as a new `number_of_children` relationship property (integer) on the marriage relationship and round-trips back to `FAM.NCHI` on export. NCHI captures the recorded child count, which can legitimately differ from the number of individually-linked children. A non-numeric payload is preserved verbatim with a warning rather than dropped; NCHI on a spouseless FAM (no relationship to attach to) now warns instead of disappearing silently. Adds the `number_of_children` entry to the `relationship-properties` standard vocabulary. (#490)
- **Evidence Explained source classification (`source_nature` / `information_type`)** — Sources can now record the two intrinsic Evidence Explained (Elizabeth Shown Mills, 4th ed., 2024) classification axes as standard source properties instead of free-text notes. `source_nature` (backed by a new `source_natures` standard vocabulary: `original`, `derivative`, `authored`) captures how the source was produced; `information_type` (backed by a new `information_types` vocabulary: `primary`, `secondary`, `indeterminate`) captures the informant's relationship to the event. Both are `vocabulary_type`-constrained, so out-of-vocabulary values surface a validation warning and archives may extend either vocabulary; the two new vocabularies are embedded in `go-glx` and registered through the same path as `legal_statuses` (`embed.go`, the `GLXFile` struct, `vocabularies.go` switch, the validation map, serializer init, and `glx/archive_io.go` merge fallback), each with a matching JSON schema wired into `glx-file.schema.json`. Documented with a new "Source Classification (Evidence Explained)" section on the Source entity page (noting that information quality recorded at the source level is the predominant/default value, that per-fact variation is recorded today via a custom `citation_properties` entry with standardization tracked in #988, and that the third *evidence* axis — direct/indirect/negative — remains an assertion-level concern). Closes #287.
- **`glx proof` command** — Compiles the evidence bearing on a specific research question about a person into a structured proof summary following the BCG Genealogical Proof Standard (GPS). `glx proof <person> --question <parentage|birth|death|marriage|identity>` gathers every assertion relevant to the question (including assertions on the person's events and relationships), resolves each assertion's citations and sources to complete, human-readable references (GPS element 2), surfaces the relevant missing records from the coverage checklist as evidence gaps (GPS element 1), flags conflicting assertions and reports whether each conflict has been resolved via the assertion `status` field — `proven` over `disproven` (GPS element 4), lists any logged research searches that document a reasonably exhaustive search, and ends with a conclusion: `PROVEN`, `PROBABLE`, `POSSIBLE`, `INSUFFICIENT EVIDENCE`, or `CONFLICTED` (GPS element 5). Output is terminal text by default, with `--format json` and `--format markdown` for tooling and research reports. (#118)
- **Temporal validation: relationship `start_event` must precede `end_event`** — `validateTemporalConsistency()` gains a fourth check: relationships that set both `start_event` and `end_event` now warn when the end event's date resolves to a year before the start event's, catching common data-entry errors like swapped marriage/divorce event references. Reported as a warning (not an error), matching the severity of the existing temporal checks (death before birth, parent younger than child, marriage before birth), because fuzzy dates and data-entry errors are common; relationships where either event reference is unset, dangling (caught separately by reference validation), or has a missing/unparseable date are skipped, and same-year boundaries (e.g. shared transfer events) do not warn. The ordering constraint is now also documented under Validation Rules in `specification/4-entity-types/relationship.md`, which previously only required that the references resolve. (#669)
- **`civil_union` and `common_law_marriage` standard relationship types** — Both are legally distinct from marriage in many jurisdictions and exist as separate categories in GEDCOM X (`CivilUnion`, `CommonLawMarriage` couple facts) and Gramps (`CIVIL_UNION`), but GLX archives previously had no standard way to record the distinction — researchers had to file both under `marriage` or `partner` (or define custom types). Added to `relationship-types.glx` (growing the standard vocabulary from 20 to 22 types) with parallel `RelationshipType*` constants and a new exported `IsCoupleRelationshipType` helper in `go-glx`. Every couple-relationship check in the CLI analysis tools (`analyze` spouse indexing, `coverage` marriage records and family-source detection, `timeline` family traversal, `summary` spouse listing) now goes through that helper, so the new types participate in analyses instead of being silently skipped. GEDCOM import semantics are unchanged: GEDCOM 5.5.1/7.0 have no dedicated tag for either (both are conventionally `MARR` with a free-text `TYPE`), so `MARR` still imports as a `marriage` relationship with the `TYPE` value preserved in the `marriage_type` property — each new vocabulary entry's comment documents this round-trip; mapping known `TYPE` values onto the new types at import time is a possible follow-up. The `partner` description gains a sentence delimiting it from both new types: `partner` stays the home for informal domestic partnership/cohabitation, while `civil_union` covers the legally formalized kind. Gramps' `UNMARRIED` is deliberately not added as a type — an unmarried couple is `partner` by definition. (#556, #1085, #1094)
- **`SECURITY.md` safe-harbor clause and coordinated-disclosure embargo policy** — Adds the two elements the OpenSSF OSPS Baseline Level 2 "coordinated vulnerability disclosure" control was missing. A **Safe Harbor** section (adapted from the [disclose.io](https://disclose.io/) Core Terms, a widely used open-source safe-harbor framework) assures good-faith researchers we will not pursue or support legal action under anti-hacking laws such as the US CFAA for accidental, good-faith policy violations, and sets the guardrails (only test your own machine and data, minimise impact, report before disclosing) that keep research inside that harbor. A **Coordinated Disclosure and Embargo** section publishes the advisory when the fix ships and treats 90 days as a backstop (the outer limit beyond which an issue should not stay embargoed indefinitely; extendable by mutual agreement), names who is inside the embargo (maintainers via the private GitHub Security Advisory draft, plus the reporter), states the embargo-conduct expectations on both sides, and documents how downstream consumers are notified — a published GitHub Security Advisory with a requested CVE that lands in the GitHub Advisory Database and the Go vulnerability database, alerting `go-glx`/`glx` users through `govulncheck`, `dependency-review`, and Dependabot. `SECURITY-POSTURE.md` is updated in step: the Level 2 coordinated-disclosure row flips from partial to met, clearing the last Level 2 gap, so the headline self-attestation advances from Level 1 (most Level 2 met) to **Level 2 (most Level 3 met)**, leaving #269 (SBOM) as the sole remaining gap. Closes #424.
- **Binary archive cache for fast repeated loading (`glx cache`)** — Every command that loads a multi-file archive re-parses every `.glx` YAML file on each run; on large archives that is tens of seconds and gigabytes of peak memory per invocation. A new opt-in binary cache persists the fully parsed archive to `{archive}/.glx/cache.bin` (via `encoding/gob`) so subsequent loads deserialize a blob instead of re-parsing YAML. New `glx cache build [--force]`, `glx cache clean`, and `glx cache status` subcommands manage it; read commands (`summary`, `query`, `timeline`, `analyze`, `stats`, `vitals`, `places`, `cite`, `cluster`, `coverage`, `diff`, `duplicates`, `evidence`, `path`, `search`, `report`, `export`, and the ancestor/descendant tree) transparently use a fresh cache when one is present. The cache is disposable and best-effort: any detected problem (missing, stale, corrupt, version/struct mismatch, implausibly large, decode failure) silently falls back to the authoritative YAML parse, so a missing, stale, or unreadable cache is ignored rather than trusted. The cache file is size-capped and decoded through a bounded reader before any gob decode, since gob is not hardened against untrusted input (a hostile cache could otherwise be planted in a shared repo). Staleness is decided solely by a stat-only `(path, size, mtime)` fingerprint over all `.glx` files (no file reads); the archive's git `HEAD` commit and clean state are also recorded (read in-process via the pure-Go `github.com/go-git/go-git/v5` library, so no `git` binary on `PATH` is required) and surfaced by `glx cache status`, but do not affect staleness. As with any mtime-based cache, a content edit that preserves a file's size and mtime is the one change the fingerprint cannot see; `glx cache build`/`glx cache clean` forces a refresh in that corner case. `GLX_CACHE=auto` additionally builds the cache on the first miss; `GLX_CACHE=off` bypasses it entirely. `glx init` now git-ignores `.glx/`, and write/transform commands keep parsing YAML directly so their output is never affected by the cache. Scoped to multi-file (directory) archives; single-file archives and parse-time memory reduction are out of scope. (#197)
- **Release binaries now carry SLSA build-provenance attestations** — The `release.yml` workflow runs `actions/attest` (pinned to the `v4.1.0` commit SHA) after GoReleaser, taking GoReleaser's `checksums.txt` as `subject-checksums` so a single attestation covers every released archive. The provenance is signed keyless via the GitHub OIDC token and stored on GitHub, letting downloaders verify a binary was built by this repo's CI with `gh attestation verify --owner genealogix <file>`. This is on top of the existing cosign keyless signing of the checksums file (the two are complementary: cosign proves the checksums file's integrity, the attestation proves build provenance per SLSA). Required adding the `attestations: write` permission to the release job. `actions/attest-build-provenance` is only a composite wrapper around `actions/attest` that forwards empty predicate inputs, so calling `actions/attest` directly — which defaults to the SLSA provenance predicate when no predicate is supplied — is equivalent. SBOM generation is tracked separately in #269. (#256)

- **Seven new standard source types in `source-types.glx`** — Added `family_bible` (Family Bible records of births, marriages, deaths — often the only pre-civil-registration source for US colonial/antebellum research), `gravestone` (tombstone/headstone inscriptions, cemetery memorials), `dna_test` (genetic test results — autosomal, Y-DNA, mitochondrial DNA), `memoir` (autobiographies, diaries, personal journals), `manuscript` (unpublished manuscripts or typescripts), `map` (historical maps, atlases, survey plats), and `social_media` (social media posts and profiles), growing the standard vocabulary from 18 to 25 types. Source type is an open vocabulary, so archives could already add these as custom types; standardizing the common ones keeps classification consistent across archives and unlocks GEDCOM round-trip. The parallel `SourceType*` constants in `go-glx/constants.go` were extended to match, and the GEDCOM `SOUR.TYPE` import mapping now recognizes the aliases `bible`/`gravestone`/`tombstone`/`headstone`/`dna`/`memoir`/`diary`/`manuscript`/`map`/`social` (explicit-value mapping, no false-positive risk) plus identity mappings for the canonical keys `family_bible`/`dna_test`/`social_media` so all seven types survive a GLX→GEDCOM 7.0→GLX round-trip (the exporter writes `Source.Type` verbatim as the `TYPE` value; without the identity entries these three would re-import as `other`). Title-based inference picks up distinctive phrases (e.g. "family bible", "headstone", "dna test", "survey plat", checked before the broad "land" keyword) while deliberately avoiding the bare word "map" so place names like "Mapleton" do not misclassify. The `source` entity spec and the vocabularies reference were updated in step. (#563)
- **Deterministic schema/code drift detection (`make check-code-drift`)** — A new Go tool under `tools/driftcheck` compares the `go-glx` type definitions (via reflection) against the JSON Schemas in `specification/schema/v1`, catching structural drift — missing/extra fields, yaml-tag mismatches, `omitempty`-vs-`required` mismatches, and type-family mismatches — on every PR with no API keys. It is the deterministic counterpart to the LLM-based `/check-code-drift` slash command: zero false positives by design, with ambiguous/semantic cases still deferred to the LLM checker. Known, by-design drift is suppressed by reading `.claude/drift-allowlist.yaml` (matching the same per-symbol identity the slash commands use). Wired into `make check`, runs as a dedicated `validate-spec` CI job, and is guarded by an in-repo regression test that fails if the committed types and schemas ever diverge. The closed-issue staleness gate noted in #797 needs issue-state lookups and remains future work. (#673)

- **Date parsing consolidated into one calendar-aware parser (`go-glx/glxdate`); year extraction no longer reads the day of month as the year** — `ExtractFirstYear` returned `1` for `1 JANUARY 1900` and `15` for `15 March 2020`, because its month regex only knew upper-case 3-letter abbreviations and GEDCOM import stored such dates raw instead of normalizing them. Since the year feeds temporal-consistency validation, duplicate detection, privacy cutoffs, coverage/gap analysis, and the `analyze` commands, a wrong year silently corrupted all of them. The root cause was three disagreeing definitions of a valid date (the importer's `parseExactDate`, the extractor's regexes, and the validator's `isValidSimpleDate`). All three now funnel through a new `glxdate` package that is the executable form of the spec's Date Format Standard: `glxdate.Parse` returns an immutable `Date` value (`Year`, `Month`, `Day`, `Precision`, `Qualifier`, `Calendar`, `IsRange`/`Start`/`End`, `Valid`, `String`), and `DateString` gains `Parse()`/`Year()`. Recovery is limited to what is unambiguous: English month names in any case or length (`1 JANUARY 1900`, `15 March 2020`, `March 15, 1850`), keyword case/punctuation (`Abt 1850`, `Bet 1880 and 1890`, `ABT. 1850`), spelled-out and circa keywords (`about 1850`, `circa 1850`, `c. 1841`, `CIR 1375`, `before 1900`, `after 1900`), a dash for `AND` after `BET` (`BET 1675 - 1740`), and a range start that borrows the end's year (`BET 07 OCT AND 08 NOV 1260`) now canonicalize on GEDCOM import (`1900-01-01`, `ABT 1850`, `BET 1880 AND 1890`, `BET 1675 AND 1740`, `BET 1260-10-07 AND 1260-11-08`), while numeric day/month forms (`15/01/1900`), dual years (`1731/32`), BCE dates, and free text are preserved verbatim and reported by `glx validate` — the parser never guesses day-vs-month order and never converts calendars. Two GEDCOM forms GLX had no spelling for are now part of the date format: the `EST` qualifier (estimated from another event's date, a sibling of `ABT`/`CAL`, not a spelling of `INT`) and the `BCE` era suffix (`510 BC` → `0510 BCE`; `Date.Year`/`ExtractFirstYear` return it as -510 so dates order across the era boundary). Dual years (`1731/32`) remain preserved verbatim pending a decision on their representation. For raw-preserved Gregorian bodies the year is still recovered by preferring a 4-digit token, so already-imported archives get correct years without re-import. GEDCOM's open-start period (`TO 1950`) is now a GLX form. Calendars are recognized on import in both GEDCOM spellings and at any grammatical position (`ABT JULIAN 1731`, `BET @#DJULIAN@ 1700 AND @#DJULIAN@ 1710`, bare `GREGORIAN 12 AUG 1401`), which previously left most of the GEDCOM 7 date fixture stored raw; GEDCOM 7 export writes the calendar as a tag before each date (`ABT JULIAN 1731`) instead of a 5.5.1 escape. The `glx query`, `glx cluster`, `glx timeline`, `glx serve`, and `glx summary` date helpers now read the parsed date instead of their own regexes, so year filters, chronological sort, and narrative dates agree with `glx validate` (a raw `1 JANUARY 1900` sorted as year 1 and `0044 BCE` sorted after `0010`). Unknown calendars now use GEDCOM 7's extension convention: the prefix starts with an underscore (`@#DROMAN@` imports as `_ROMAN` and exports back as `@#DROMAN@` for 5.5.1 or as the `_ROMAN` tag for 7.0), which is what lets the parser tell a calendar from free text. GEDCOM 5.5.1 export writes the era as `B.C.` and 7.0 as `BCE`. Also fixed along the way: a full month name in upper case (`APRIL 1688`) or a free-text word (`LIVING 1515`, `CLASS OF 1905`, `AFTER 1839 BEFORE 1840`) was treated as an unknown calendar prefix and accepted as valid, a Hebrew or French Republican date missing its year (`HEBREW 15 TSH`) reported the day of month as the year, and validation accepted any string containing a keyword substring (`OCTOBER 1850` passed because it contains `TO`) — date-format warnings now cite the specific reason. The GEDCOM encoding of dates lives in the same package (`glxdate.FromGEDCOM`, `glxdate.Canonicalize`, `Date.GEDCOM`), so GEDCOM export renders from the parsed date instead of re-splitting the stored string: `INT` dates now export with GEDCOM month spelling (`INT 15 MAR 1850 (text)` rather than `INT 1850-03-15 (text)`), a non-canonical body like `1850-3-5` is exported as stored rather than guessed into `5 MAR 1850`, and preserved bodies export with keywords upper-cased and whitespace collapsed (`abt. 1532 (or by '12?)` → `ABT 1532 (or by '12?)`). The `glx timeline`/`serve`/`summary` sort key is five digits wide so a five-digit Hebrew or extension-calendar year sorts after `9999` rather than before it. The parser is fuzz-tested and verified against a corpus of ~7,000 real-world GEDCOM `DATE` values sampled by shape from ~700k lines across ~250 files; a golden file beside the corpus pins the parse, stored, and exported outcome of every line. Fixes #1025.
- **`glx rename` rewrites only the files it changes and never swaps the archive directory** — On a multi-file archive, `rename` used to load everything, apply the rename in memory, and write a complete fresh serialization through the temp-directory swap shared with `migrate` and `merge`. That had two visible consequences. The archive directory was replaced by a new inode, so a shell sitting in the archive root (or an editor with entity files open) was left pointing at the now-deleted original — `ls` showed an empty directory until `cd .` — and every file in the archive was re-emitted in the serializer's canonical one-entity-per-file layout and formatting, so a two-event `events/event-births.glx` became two files, single-entity files were renamed to match their entity ID, unrelated files picked up indentation and quoting changes, and the standard vocabularies were materialized into `vocabularies/`. Rename now validates against the whole archive as before (old ID present, new ID free) but then treats each file as an independent fragment: files that neither define nor reference the old ID are not touched at all, files that do are rewritten in place at the same path, multi-entity files stay multi-entity, and only a single-entity file whose name is the old ID is moved to the new name (refusing if that path already exists). Each file write is atomic (temp file plus rename, so a full disk cannot leave a truncated file), and the original bytes of every touched file are held in memory and restored if any write fails, so a failed rename cannot leave the archive inconsistent; recovery state is not persisted across a crash mid-rename, which is the accepted trade against the directory swap. Before anything is written the plan is checked: the new ID must be a valid filename even when its entity lives in a multi-entity file, a symlinked `.glx` file is refused rather than written through (the loader follows symlinks when reading, so one could otherwise redirect a write outside the archive), a file whose bytes on disk no longer match what was loaded is refused (a concurrent edit, or a Git symlink placeholder on Windows with `core.symlinks=false` that the loader resolved to its target), and a file move is refused if the target already exists including on case-insensitive filesystems. `--dry-run` runs those same plan checks, so it fails on a rename the real write would refuse instead of reporting a success the user cannot actually get, and nothing is printed until the plan is known to be applicable, so a failed run no longer emits a success line it did not earn. A plan that targeted the same path twice is refused up front, since the second write would clobber the first and rollback could not restore the state in between. The summary line counts "change(s)" rather than "reference(s)": the number includes the entity's own map key alongside the reference fields it rewrote, and `RenameResult.RefsUpdated` in `go-glx` now documents that. On a multi-file archive a new ID that differs only by case from another entity's ID is rejected, since the two would collide on the lowercased filenames the writer derives (renaming an entity to a case variant of its own ID is still allowed and keeps the file's on-disk name; single-file archives, which derive no filenames, are unaffected). File permission bits are preserved on rewrite, move, and rollback, and on the single-file-archive form of the command, so a private entity file never becomes world-readable through a rename. The duplicate-entity-ID warnings this path prints are sanitized for the terminal like every other archive load's (#925), since it deserializes directly rather than through `LoadArchiveWithOptions`. A file that moves is reported as one touched file rather than two, matching what lands on disk. An archive that defines the same ID under two entity types has only the type `RenameEntity` selects renamed, matching the previous whole-archive behaviour. Rewritten files still take the serializer's formatting; byte-exact preservation of untouched lines within a changed file is not attempted. Adds `RenameInFragment`, `GLXFile.HasEntity`, `GLXFile.EntityIDIgnoringCase`, and `ErrEntityAlreadyExists` to `go-glx`. `migrate` and `merge`, which legitimately rewrite most of an archive, keep the swap. Also adds an end-to-end CLI test harness under `glx/e2e/` that builds the real binary and runs it as a subprocess; `rename` is the first command covered, including the run-from-inside-the-archive case from the report. Fixes #1192. Fixes #1197.
